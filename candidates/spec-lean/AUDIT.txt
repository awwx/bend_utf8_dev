  returns (b31..b24), ..., (b7..b0).

C1 (concern, low): bit8_value_word is close to definitional in Lean.
  bit8_value is UInt8.ofBitVec (ofBoolListLE [b0..b7]), and the law
  compares that with UInt8.ofNat (ofBoolListLE [b0..b7]).toNat.  So
  in Lean the "independent check" checks little beyond ofBitVec =
  ofNat . toNat.  Bend's version is similarly shallow: the same WCon
  chain, checked against Word.to_nat.  The independent content in both
  is bit8_value_sum, which is arithmetic and which `decide` proves in
  Lean.  If ofBoolListLE were MSB-first, bit8_value_sum would be false.
  No change needed.

C2 (info): Lean's OfNat UInt8 wraps silently: (300 : UInt8) = 44.
  Every byte literal in the file is at most 255, so nothing is affected
  today.  Anyone editing the examples later should watch for it.

N1 (agreed deviation 1, effect on meaning; corrects TRANSLATION.txt)
  Bend quantifies its byte lists over all U32 values.  This applies to
  begins_with_scalar_unique, maximal_subpart_*, decodes_first_*,
  decodes_exists/unique, and `rest` in utf8_decode_buffer_safe, which has
  no all_bytes guard.  Lean quantifies over UInt8 lists, so these laws
  are formally weaker.  TRANSLATION.txt says the safe law is "weaker than
  Bend's, but only outside the byte domain".  In substance it is not
  weaker.  A value v > 255 never appears in any encoding: lead bytes are
  at most F7 and continuation bytes at most BF.  So a list beginning with
  v has no valid sequence at the front, and no valid sequence prefix
  contains v.  Every Bend definition therefore treats v exactly as it
  treats 0xFF.  Replacing each value > 255 by 0xFF keeps decodes(bytes,
  text) unchanged, so each Bend law over U32 lists follows from its
  byte-list version.  No meaning relevant to the decoder is lost.  The
  prompt law needs no such argument, since Bend already restricted rest
  to bytes there.
