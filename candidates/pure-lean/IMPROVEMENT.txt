PROFILE FINDINGS (set_option trace.profiler / profiler, v4.36.0-rc2)
  Utf8Table: completion_spec took 76 of ~85 s (three omega calls of 22, 12
    and 9 s, many smaller, maxHeartbeats raised to 2000000).  Cause: the
    `byte_table` macro rewrote everything at once (secondOk_iff, a 5-way
    disjunction, plus isLead*/isCont ranges and the toNat value of cpOf)
    and handed omega whole-table goals; omega then case-split on byte
    values and disjunctions.  The rest: encodes_of_isVS 2.3 s,
    isVSP_of_isVS_append 2.6 s, isVS_of_encodes 1.5 s, isVS_isVSP 1.0 s.
  Utf8Bits: each of one/two/three/four_shape had omega calls of 1-4 s plus
    0.5-1.2 s kernel checking.  Cause: every goal had all 25-32 bit atoms
    `cp.toNat / 2^i % 2` in context (each becomes several omega variables
    with div/mod constraints); omega had to rediscover how they combine.
    Giving omega the explicit 32-term bit sum made it slower (timeouts;
    17 s with the bits generalised to variables): the number of div/mod
    atoms in one omega call is the cost, not missing facts.

WHAT CHANGED
  Utf8Bits: bounds without omega (Nat.testBit_lt_two_pow for "below 2^k ->
    high bits clear", Nat.lt_pow_two_of_testBit for the converse, one bit
    position at a time); byte values one byte per omega call, with only
    that byte's <= 8 bits and `lowBits (n / 2^k) b = n / 2^k % 2^b` in
    context (macro byte_value).  Statements of the shape lemmas, enc32 and
    encoding_eq unchanged.
  Utf8Table: completion_spec splits on the lead class (isLead2/3/4 as
    Bools), not on byte values; "cpOf <> U+FFFD" because every completion
    ends in 0x80, so the code point is 0 mod 64 while 0xFFFD is 61 mod 64.
    New lemmas secondOk_80, secondOk_secondLo.  isVS_isVSP,
    isVSP_of_isVS_append, isVS_not_proper are Bool reasoning (simp_all)
    plus three disjointness lemmas lead1_not/lead2_not/lead3_not; no omega.
    secondOk_iff proved by `split` on the definition's ifs instead of 16
    by_cases and a `first | omega | ... | simp_all <;> omega` combinator.
    Removed: the `byte_table` macro, `set_option maxHeartbeats 2000000`,
    unused simp arguments.  cpOf_one..four, encodes_of_isVS, isVS_of_encodes
    unchanged (fast enough: 0.2-2 s each).
  No linter warnings remain on either toolchain.

BV_DECIDE VS ARITHMETIC (measured; delivered version uses neither bv_decide
nor native_decide)
  Micro-benchmark, same four facts each way (2-, 3-, 4-byte valid sequence ->
  code point range incl. "not a surrogate"; completion code point <> U+FFFD),
  in scratch bv/BvTest.lean and bv/ArTest.lean:
    bv_decide:  0.38 s wall per file (v4.36.0-rc2), 0.37 s (v4.35.0)
    arithmetic (toNat + omega with the lemmas above): 0.46 s
  Axioms: each bv_decide call adds its own axiom, e.g.
    'bv_two' depends on axioms: [propext, Classical.choice, Quot.sound,
                                 bv_two._native.bv_decide.ax_1_6]
    axiom bv_two._native.bv_decide.ax_1_6 :
      Std.Tactic.BVDecide.Reflect.verifyBVExpr bv_two._expr_def_1_2 bv_two._cert_def_1_2 = true
  i.e. the LRAT certificate check is run by compiled code and its result is
  trusted as an axiom (the compiler and the native code are trusted; the
  kernel does not re-check).  The first agent's all-bv_decide version
  passed check.sh in 52 s on the old VM (journal) and produced ~870 lines of
  such axioms.  With well-shaped lemmas the arithmetic route is as fast as
  bv_decide here, so there is no case for it.  It also needs
  `import Std.Tactic.BVDecide`.
